# 原稿の制作と内容確認

2026-09-23。最初の対象は『オデュッセイア』（2026年）、当面の掲載は1作品、内容確認担当は中野さん。選定と受入の状態は[最初の1作品の記録](verification/first-work.md)に置く。

## 下書きから生成対象まで

1. AIが一次資料や専門機関の資料を調査し、JSONとMarkdownを `draft`、`review: null` で作成する。資料の参照日は閲覧した日とし、人の確認日と区別する。
2. 各記述に根拠レコードを付ける。出典の発行者・URL・該当箇所、支える主張、判断の限界を記録する。歴史、作中の描写、本人の発言、編集者の解釈を分ける。
3. `npm run validate:content` で形式と参照を確認する。通過は事実の正確性や掲載可の証明にはならない。
4. 中野さんが原稿と資料を読み、見出し・概要・関係の理由・地図・年表・リンク先を含めて確認する。事実、区分、ネタバレ、素材条件に修正があれば下書きを直す。
5. 対象IDとrevisionを特定できる確認結果を受領後、確認者・確認日・対象revisionを記録して `reviewed` にする。担当就任への「はい」を原稿の内容確認として使わない。人の内容確認をAIの調査やコードレビューで代替しない。
6. 掲載対象を選び、必要な作品・記述・関係・根拠・出典を揃えて `published` にする。ここでのpublishedはローカルの静的生成対象を意味する。
7. 原稿検証と通常ビルドを実行し、PC・スマートフォンで本文、地図、年表、出典、人物との往復を確認する。中野さんが最初の1作品を受け入れてから追加作品へ進む。サービスの外部公開は別の明示依頼を要する。

## 修正・取り下げ

本文、見出し、概要、URL、関係、座標、年代、ネタバレ条件を変えたレコードはrevisionを進め、draftへ戻してreviewをnullにする。関連する根拠や出典も変更した場合は同様に更新する。人の確認担当はGit差分とrevisionを照合する。公開済みの内容を修正する場合は公開参照の整合性を保ち、再確認前の版を配信しない。

取り下げは `withdrawn` とし、そのレコードへの公開関係も同じ変更で整理する。再生成後に古いページ・JSON・素材が残っていないことを確認する。

## 素材・引用・確認画面

画像、ポスター、写真、原文の引用、外部地図を使う場合は取得元・制作者・利用条件・必要表示・改変・確認者と確認日を記録する。条件未確認の素材を完成データへ混ぜない。今回の初稿は自作の要約と数値による概略図のみで、画像・映像・原文引用を転載していない。出典ページを参照したことと、その素材の転載許可を得たことは区別する。

内容確認用の下書きを表示する場合は通常のdistと分離し、ローカル限定の画面に「下書き・内容確認前」と明記する。確認のためにreviewやpublishedを仮入力しない。外部資料には本編の詳細を含む場合があるため、リンクを開く前にその旨を知らせる。

確認画面はリポジトリ直下で `npm run review:content` を実行し、[127.0.0.1:4326](http://127.0.0.1:4326/)を開く。出力先は `.runtime/content-review`。原稿の変更後はコマンドを再起動する。現段階では、未確認の下書きだけを扱い、ネタバレ指定・引用・素材を含む原稿は生成を拒否する。
